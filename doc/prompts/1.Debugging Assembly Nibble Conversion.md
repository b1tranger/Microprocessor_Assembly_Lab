## 3. Model Thinking & Internal Reasoning

```text
Examining Hex Conversion:
I've been meticulously examining the hex conversion routine, specifically lines 44-56 in the provided assembly file. The conditional jump based on the comparison to 57 is crucial, differentiating between numeric and alphabetic hex characters. The routine cleverly handles the offset for A-F. Now, I'm digging into how this interacts with the overall printing process.

Analyzing the Output:
I've zeroed in on the `print_hex` procedure. The critical error is using `mov al, 02h` for the DOS character display. This leaves `ah` with whatever was there previously, which likely contains the value `09h` or other garbage, leading to unpredictable string printing via `int 21h` with `dx` containing `al`. That seems to be the root of the problem. Also, the hex conversion logic appears sound: it correctly converts 0-9 to ASCII '0'-'9' and A-F to ASCII 'A'-'F'.
```

---

## 4. Model Response & Solution

The issue is in your **`print_hex`** procedure on line 52:

```assembly
   out:
    mov dl, al
    mov al, 02h    ; <--- BUG: This sets AL, not AH!
    int 21h
    ret
```

### Why it causes special characters:
* **DOS Service 02h (Character Output)** expects the function code in **`AH`** (`mov ah, 02h`), not `AL`.
* Because `AL` was modified instead of `AH`, `AH` remained `09h` (from line 16).
* When `int 21h` is called with `AH = 09h`, DOS treats `DX` as a pointer to a `$`-terminated string. Since `DX` only contained the character's ASCII value (e.g., `0044h`), DOS printed raw memory bytes starting from address `0044h` until it found a `$` character, printing gibberish and special characters.

### Corrected `print_hex` Procedure:

```assembly
print_hex proc
    add al, 48
    cmp al, 57
    jbe print_char
    add al, 7
    
print_char:
    mov dl, al
    mov ah, 02h        ; Set AH = 02h for single-character print
    int 21h
    ret
print_hex endp
```

# Part 2: Debugging Premature DOS Exit & Multi-Line Execution (`A_3.asm`)

## 1. User Request

```text
this is the expected output of the code @[A_3.asm] :
num1: 08 
num2: FB

but the code run stops in Emu8086 after printing each line. Say the code output shows `num1: 08` then a message prints:

then I have to run the code again without clearing the terminal to get the next expected output, and after 6 consecutive runs, i get the full output. on 7th run the program breaks and loops infinitely through the registers.
```

### Context & Metadata
- **Active Document**: `A_3.asm` (Assembly 8086)
- **Cursor Position**: Line 1 / Line 209

---

## 2. Code Inspected

```assembly
.model small
.stack 100h
.data
    num1 db 018h 
    num2 db 02Ah
    num3 db 0C4h
    num4 db 06Bh
    num5 db 0FFh
    num6 db 07Ah
    
    msg1 db "num1 : $"  
    msg2 db "num2 : $"  
    msg3 db "num3 : $"  
    msg4 db "num4 : $"  
    msg5 db "num5 : $"  
    msg6 db "num6 : $"  
 
.code   
    main proc 
        mov ax, @data
        mov ds, ax
        
        ;NUM 1 | AND op 
        mov dx, offset msg1
        mov ah, 09h
        int 21h
        
        mov al, num1
        and al, 0Fh
        mov bl, al  
                
        ; PRINT
        mov al, bl 
        shr al, 4
        call print_hex
        
        mov al, bl
        and al, 0Fh
        call print_hex
        
        mov ah, 4Ch        ; Premature termination
        int 21h
        
        ; NEWLINE and CARRY BACK (Trapped behind exit)
        mov ah, 2
        mov dl, 10
        int 21h
        mov dl, 13
        int 21h
        
        ; ... Repeated across num2 through num6 ...
```

---

## 3. Model Thinking & Internal Reasoning

```text
Examining the code flow in A_3.asm:
1. `mov ah, 4Ch` followed by `int 21h` is the DOS interrupt service to terminate execution and return control to the operating system.
2. In the user's code, this exit call was duplicated inside each calculation block (after printing num1, after printing num2, etc.), placed *before* the newline instructions.
3. Why did it behave as described?
   - On the first run, the CPU printed num1 (08) and executed `INT 21H, AH=4Ch`, halting execution with "PROGRAM HAS RETURNED CONTROL TO THE OPERATING SYSTEM".
   - The newline instructions directly below it were never executed.
   - When the user hit "Run" in Emu8086 without resetting IP / re-assembling, the emulator resumed execution at the next byte (which was the newline code). It printed the newline, computed/printed num2, and hit the next `int 21h` exit.
   - After 6 runs, all 6 numbers and 5 newlines had been output.
   - On the 7th run, execution resumed after the 6th exit and fell through directly into the `print_hex` procedure without a `call`. When `print_hex` hit `ret`, it popped invalid data off the stack, causing register runaway and an infinite loop.
4. Solution:
   - Remove the premature `mov ah, 4Ch / int 21h` calls from each section.
   - Move newline printing (CR 13, LF 10) directly after each number is printed.
   - Place a single `mov ah, 4Ch / int 21h` termination at the very end of `main proc`.
   - Rename label `out` in `print_hex` to `print_char` because `OUT` is a reserved 8086 port I/O mnemonic.
   - Separate the clean fixed version into `A_3_FIXED.asm` and preserve `A_3.asm` for comparison.
```

---

## 4. Model Response & Solution

### Root Causes
1. **Premature Termination (`INT 21H, AH = 4Ch`)**: Calling DOS function `4Ch` halts the program immediately. Placing it after each number caused the program to stop after printing just one line.
2. **Execution Fallthrough & Emulator State**: Resuming an already-stopped program in Emu8086 advances the instruction pointer `IP` to the subsequent instruction without resetting state, eventually falling into subroutine code (`print_hex`) without a valid stack frame.

### Fixed Code Implementation: [`A_3_FIXED.asm`](file:///c:/Users/gsmur/Documents/GitHub/UITS/Microprocessor_Assembly_Lab/A_3_FIXED.asm)

- Only one `mov ah, 4Ch; int 21h` at the end of `main proc`.
- Proper newline sequence (CR = 13, LF = 10) placed immediately after each hex output.
- Label `out` renamed to `print_char` to avoid conflicts with the x86 `OUT` instruction.
