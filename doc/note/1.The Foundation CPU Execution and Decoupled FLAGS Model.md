# 1. The Foundation: CPU Execution & The Decoupled FLAGS Model

This document explains the two-step decoupled execution model of the 8086 CPU—how condition evaluation is strictly separated from branch decisions via the hardware FLAGS register.

## 1. Overview: The Decoupled Condition-Branch Model

In high-level languages like C/C++, Java, or Python, a condition and a branch are written as a single composite statement:
```c
if (a > b) {
    do_something();
}
```

In the 8086 CPU architecture, **this single operation is strictly split into two independent machine cycles**:

```
+-------------------------------------------------------------------------+
| STEP 1: ALU Evaluation (Arithmetic / Logic)                             |
| Instruction: CMP, TEST, SUB, AND, etc.                                  |
| -> Computes intermediate result.                                        |
| -> Discards the result (does NOT alter destination for CMP/TEST).       |
| -> Updates Hardware Status Bits in the FLAGS Register.                  |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
| 8086 FLAGS Register Status Bits:                                        |
| [ ... | OF | DF | IF | TF | SF | ZF | AF | PF | CF ]                   |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
| STEP 2: Control Transfer Decision (Branching)                           |
| Instruction: JZ, JNE, JA, JB, JG, JL, etc.                              |
| -> Reads ONLY the flag bits (does not know or care about a or b).       |
| -> If flag condition is MET: IP = Target Address.                       |
| -> If flag condition FAILS: IP advances to next sequential instruction. |
+-------------------------------------------------------------------------+
```

---

## 2. Step 1: ALU Evaluation Cycle

The first instruction performs a comparison or arithmetic operation. For example:
```assembly
cmp ax, bx
```
- The ALU internally calculates `AX - BX`.
- The numerical difference is **discarded** (neither `AX` nor `BX` changes).
- The hardware status flags (`ZF`, `CF`, `SF`, `OF`, `PF`, `AF`) are updated based on the result.

---

## 3. Step 2: Control Transfer Decision (Branching)

The second instruction inspects one or more flags in the FLAGS register:
```assembly
je target_label
```
- The jump instruction **never sees** `AX` or `BX`. It only reads the Zero Flag (`ZF`).
- If `ZF = 1` (meaning `AX - BX == 0`, so `AX == BX`), `IP` is loaded with `offset target_label`.
- If `ZF = 0`, execution simply falls through to the next sequential instruction.

---

## 4. The 6 Key Status Flags in 8086

| Flag Mnemonic | Flag Name | Set Condition (`= 1`) | Cleared Condition (`= 0`) |
| :--- | :--- | :--- | :--- |
| **`ZF`** | Zero Flag | Result is strictly $0$ (operands equal) | Result is non-zero |
| **`CF`** | Carry Flag | Unsigned arithmetic borrow or carry ($A < B$) | No borrow/carry generated |
| **`SF`** | Sign Flag | Highest bit of result is `1` (negative) | Highest bit is `0` (positive/zero) |
| **`OF`** | Overflow Flag | Signed arithmetic capacity exceeded | Result fits within signed bounds |
| **`PF`** | Parity Flag | Lowest 8 bits contain an **even** number of `1`s | Odd number of `1`s |
| **`AF`** | Auxiliary Carry | BCD carry from bit 3 to bit 4 (nibble carry) | No half-carry |

## 5. High-Level Language vs. Assembly Comparison

```c
// High-Level Language (Combined)
if (x == 0) {
    status = 1;
}
```

```assembly
; 8086 Assembly (Decoupled Evaluation and Branch)
    cmp x, 0             ; Step 1: ALU evaluates (x - 0) and sets ZF
    jne skip_assignment  ; Step 2: Branch decider checks ZF flag
    mov status, 1        ; Body executed only if ZF == 1
skip_assignment:
```
