\begin{abstract}
Conventional Network Attached Storage (NAS) devices and web servers typically depend on full operating systems and power-hungry single-board computers or x86 processors. In this project, we implement a compact, low-power micro-NAS and static web server built around the ESP32-WROOM-32 microcontroller. Using FreeRTOS task separation, the hardware VSPI bus, and chunked HTTP streaming, the node operates as a local wireless file server capable of handling multipart file uploads, binary downloads, live storage telemetry, and static HTML/CSS web hosting without external cloud dependencies.
\end{abstract}

\begin{IEEEkeywords}
ESP32, Embedded Systems, FreeRTOS, Micro-NAS, VSPI, FAT32, Web Server.
\end{IEEEkeywords}

\section{\textbf{Introduction}}
Local data sharing and lightweight web hosting in embedded and field environments often do not justify the power draw or hardware cost of full Linux-based systems such as a Raspberry Pi, which typically consumes between 3 and 7 Watts under load. By comparison, an ESP32 microcontroller costs roughly \$4 and runs below 1 Watt while offering dual-core processing and integrated 802.11 b/g/n Wi-Fi.

In this work, we develop an embedded NAS and static website host on the ESP32 platform, validated using PlatformIO and a local Wokwi hardware simulation bridged to physical network interfaces via `wokwigw`. By interfacing a FAT32-formatted MicroSD card over the dedicated VSPI bus, our firmware supports browser-based file uploads, direct binary downloads, protected system directories, and static webpage delivery across local Wi-Fi and Ethernet networks without requiring client-side software installation.

\section{\textbf{Project Overview \& Objectives}}

\subsection{\textbf{Problem Statement \& Solution}}
Microcontrollers have strict memory limits—specifically 520 KB of internal SRAM on the ESP32, with roughly 320 KB available for the dynamic heap. Buffering entire multi-megabyte files in RAM during HTTP transfers causes immediate heap exhaustion and system resets. Additionally, blocking SD card block writes can stall network packet handling.

To solve both issues, our design separates network protocol handling on Core 0 from HTTP request routing and SD sector I/O on Core 1 via FreeRTOS. For file transfers, incoming multipart TCP payloads are accumulated into a fixed 4,096-byte sector-aligned RAM buffer before being flushed to the FAT32 card, keeping runtime memory overhead constant regardless of file size.

\subsection{\textbf{Core Objectives}}
\begin{itemize}
    \item Build a localized, browser-accessible file storage system on an ESP32 microcontroller using the hardware VSPI interface.
    \item Develop a responsive web dashboard with live storage metrics, recursive file listing (`/api/files`), and write-protection for system assets.
    \item Support dual-mode operation: serving binary file downloads alongside static HTML5/CSS/JS web pages from the `/www/` directory.
    \item Verify system stability, memory usage, and multi-device LAN accessibility across both simulated and physical network bridges.
\end{itemize}

\section{\textbf{System Architecture \& Working Principle}}

\subsection{\textbf{Key Components \& Specifications}}
The system combines hardware peripherals and firmware modules tuned for constrained SRAM environments:
\begin{itemize}
    \item \textbf{Microcontroller:} ESP32-WROOM-32 (Xtensa Dual-Core 32-bit LX6 microprocessor at 240 MHz, 520 KB SRAM, and 4 MB SPI Flash).
    \item \textbf{Storage Subsystem:} MicroSD card module formatted in FAT32, connected to the VSPI hardware peripheral (GPIO 5, 18, 19, 23) and clocked at 4 MHz for reliable block-write timing.
    \item \textbf{Network Subsystem:} Integrated 2.4 GHz Wi-Fi radio running the LwIP TCP/IP stack and the native Arduino-ESP32 `WebServer` on port 80, bridged to host LAN/hotspot interfaces on port 9080 during simulation.
    \item \textbf{Firmware Memory Management:} Default web interfaces (`/www/fileserver.html`, `/www/index.html`) and sample reports are converted at build time into `PROGMEM` byte arrays (`default_assets.h`) and streamed via `FPSTR()` directly from Flash ROM.
\end{itemize}

\subsection{\textbf{Working Method \& Execution Flow}}
The firmware executes through a two-phase initialization and runtime sequence:
\begin{enumerate}
    \item \textbf{Phase 1 (Storage Initialization \& Seeding):} The firmware explicitly binds the VSPI pins (`SPI.begin(18, 19, 23, 5)`) and mounts the FAT32 volume. It verifies or creates `/default`, `/www`, and `/uploads`, calculates total and used storage (`SD.totalBytes()` and `SD.usedBytes()`), and seeds default assets from Flash ROM if they are missing.
    \item \textbf{Phase 2 (Network \& HTTP Service):} After associating with the Wi-Fi access point, the node binds REST and static routes (`/`, `/site`, `/api/files`, `/get`, `/upload`, `/delete`) and starts listening on port 80. A FreeRTOS diagnostic task (`xTaskCreatePinnedToCore`) runs stream-drained loopback checks on Core 1 to verify endpoint health without leaking open sockets.
\end{enumerate}

\subsection{\textbf{Firmware Implementation}}
The firmware routes HTTP requests and streams files in 4 KB sector-aligned blocks using the core setup shown below:

\begin{lstlisting}
#include <WiFi.h>
#include <WebServer.h>
#include <SPI.h>
#include <SD.h>

#define SD_CS_PIN 5
#define UPLOAD_BUF_SIZE 4096

WebServer server(80);
static uint8_t uploadWriteBuffer[UPLOAD_BUF_SIZE];

void setup() {
    Serial.begin(115200);
    SPI.begin(18, 19, 23, SD_CS_PIN);
    if (!SD.begin(SD_CS_PIN, SPI, 4000000)) {
        Serial.println("[ERROR] SD Init Failed");
        return;
    }
    WiFi.begin("SSID", "PASSWORD");
    while (WiFi.status() != WL_CONNECTED) {
        delay(200);
    }
    server.on("/", HTTP_GET, handleRoot);
    server.on("/site", HTTP_GET, handleSite);
    server.on("/api/files", HTTP_GET, handleApiFiles);
    server.on("/get", HTTP_GET, handleDownload);
    server.on("/upload", HTTP_POST, handleUploadComplete, handleFileUpload);
    server.on("/delete", HTTP_GET, handleDelete);
    server.begin();
}

void loop() {
    server.handleClient();
}
\end{lstlisting}

\section{\textbf{Project Scope and Limitations}}

\subsection{\textbf{Electrical Stability \& Memory Constraints}}
On physical hardware, MicroSD flash page writes can draw transient current spikes up to 200 mA. Combined with Wi-Fi transmission bursts, peak current demand can exceed 500 mA, which may trigger brownout resets if powered over weak USB cables. Placing a 10 $\mu$F electrolytic capacitor and a 0.1 $\mu$F ceramic decoupling capacitor across VCC and GND stabilizes the 3.3V rail. On the software side, keeping HTTP headers and TCP buffers active leaves roughly 250--300 KB of usable heap, limiting practical concurrency to 4--8 simultaneous browser clients. Additionally, unencrypted HTTP is used rather than HTTPS because TLS handshakes consume roughly 45 KB of heap per session and cannot use trusted public certificates on local private IP subnets.

\section{\textbf{Conclusion}}
This project demonstrates that an ESP32 microcontroller can reliably serve as an energy-efficient, zero-install edge NAS and static web host. By pairing FreeRTOS dual-core task isolation with 4 KB sector-aligned upload buffering, `PROGMEM` asset storage, and write-protected system directories, the firmware avoids heap exhaustion while maintaining responsive file transfers across desktop and mobile browsers. In off-grid deployments, switching the Wi-Fi driver to SoftAP mode allows the node to operate as a self-contained wireless file hub without an external router or host computer.
