# Keyboard Input Mechanics, Register Directionality, and Bit-Width Handling (4.1_CP.asm)

In 8086 assembly programming, capturing user input from the keyboard and converting it into numeric data for calculation (such as adding student marks or computing averages) requires interacting with MS-DOS operating system services via software interrupts (`INT 21h`).

## 1. Register Directionality: Why AH is Written, but AL is Read

In [`4.1_CP.asm#L55-L58`](https://github.com/b1tranger/Microprocessor_Assembly_Lab/blob/main/LabCodes/lab-4_Marks_Calculation/4.1_CP.asm#L55-L58):

```assembly
mov ah, 1          ; Staging the DOS service number
int 21h            ; Invoking DOS software interrupt
sub al, 48         ; Operating on the return value!
mov num2, al       ; Storing the result
```

A beginner often asks: *"Why did I put `1` into `AH`, but then immediately operate on `AL`?"*

### The Calling Convention of MS-DOS Interrupt `21h`
The 8086 processor does not have built-in hardware knowledge of keyboards or monitors; it delegates these I/O operations to the operating system (MS-DOS) through **Software Interrupt `21h`**.

To execute an OS task, DOS establishes a strict two-way communication contract:
1. **Input Parameter to DOS (`AH`)**: You must tell DOS **which service** to execute by loading a service function number into `AH`.
   - `AH = 01h`: Keyboard Character Input with Echo.
   - `AH = 02h`: Single Character Output (reads glyph from `DL`).
   - `AH = 09h`: String Output (reads string address from `DX`).
   - `AH = 4Ch`: Terminate Process with Return Code.
2. **Output Return Value from DOS (`AL`)**: When DOS finishes executing Service `01h`, it places the result (the ASCII byte of the key the user pressed) into **`AL`**.

```
+-------------------------------------------------------------------------+
|                  DOS SERVICE 01H CALLING CONVENTION                     |
+-------------------------------------------------------------------------+
|  YOUR PROGRAM                              MS-DOS OPERATING SYSTEM      |
|  +--------------------+                    +-------------------------+  |
|  | MOV AH, 1          |                    | (Interrupt Vector Table)|  |
|  | (Selects Service)  |                    | Vector 21h points to    |  |
|  +--------------------+                    | DOS Kernel ISR Handler  |  |
|           |                                +-------------------------+  |
|           v                                             |               |
|  +--------------------+    Software Interrupt           v               |
|  | INT 21h            | -------------------------> Halts execution      |
|  +--------------------+                            Waits for keystroke  |
|           ^                                        Echoes char to screen|
|           |        Returns keystroke ASCII byte         |               |
|           +---------------------------------------------+               |
|           |                                                             |
|           v                                                             |
|  +--------------------+                                                 |
|  | SUB AL, 48         | (Operates on the ASCII byte returned in AL!)    |
|  | MOV NUM2, AL       |                                                 |
|  +--------------------+                                                 |
+-------------------------------------------------------------------------+
```

Therefore:
- `mov ah, 1` does **not** store user data. It is a **command selection code** sent to DOS.
- `AL` is populated by DOS with the **actual character byte**.

## 2. Dissecting Lines 55–58 in `4.1_CP.asm`

Let us trace each instruction line by line:

```assembly
55:     mov ah, 1
```
- Loads immediate value `01h` into `AH`.
- Tells DOS: *"The next interrupt should wait for a keyboard keystroke and echo it to the screen."*

```assembly
56:     int 21h
```
- Transfers control to the DOS kernel interrupt service routine (ISR).
- Program execution blocks (pauses) until the user strikes a key (e.g., `'7'`).
- DOS prints `'7'` on the screen.
- DOS stores the ASCII code of `'7'` (`37h` / $55$ decimal) into register **`AL`**.

```assembly
57:     sub al, 48
```
- Subtracts $48$ (`30h`) from `AL`.
- In ASCII, `'7'` is represented by code $55$.
- Calculation: $55 - 48 = 7$.
- `AL` now contains the pure numeric integer **$7$** (`0000 0111b`).

```assembly
58:     mov num2, al
```
- Copies the pure numeric integer $7$ from `AL` into memory variable `num2`.

## 3. The Role of `SUB AL, 48` (ASCII to Numeric Conversion)

Keyboards produce **character glyph codes**, not numerical values:

| Character Pressed | Raw ASCII Received in `AL` (Hex) | Raw ASCII Received in `AL` (Binary) | After `SUB AL, 48` (Hex) | After `SUB AL, 48` (Binary) | Numeric Value |
| :---: | :---: | :---: | :---: | :---: | :---: |
| `'0'` | `30h` (48d) | `0011 0000b` | `00h` (0d) | `0000 0000b` | 0 |
| `'1'` | `31h` (49d) | `0011 0001b` | `01h` (1d) | `0000 0001b` | 1 |
| `'5'` | `35h` (53d) | `0011 0101b` | `05h` (5d) | `0000 0101b` | 5 |
| `'9'` | `39h` (57d) | `0011 1001b` | `09h` (9d) | `0000 1001b` | 9 |

Notice the pattern in ASCII:
- The upper 4 bits (upper nibble) are always `0011b` (`3h`).
- The lower 4 bits (lower nibble) represent the actual numeric digit!
- Subtracting `48` (`30h`) simply strips away the upper `0011b` prefix, converting the character code into a pure integer value.

## 4. Does the Code Differ if Values Exceed 4 Bits?

This question involves two crucial dimensions:
1. **Can `AL` hold values larger than 4 bits?**
2. **Does the input/arithmetic/output code change if values exceed 4 bits (or exceed single-digit $0\text{–}9$)?**

---

### 4.1 Hardware Bit-Width: AL is an 8-Bit Register, Not 4-Bit

`AL` is an **8-bit register** ($1\text{ byte} = 8\text{ bits}$).
- It holds values from **$0$ to $255$** (unsigned) or **$-128$ to $+127$** (signed).
- It is **never restricted to 4 bits**.

In fact, when `int 21h` returns:
- `AL` contains `'7'` = `37h` = `0011 0111b` (a full 6/8-bit value!).
- After `sub al, 48`, the single decimal digit $0\text{–}9$ happens to fit within 4 bits ($0000b \dots 1001b$ because $2^4 = 16$), but all 8 bits of `AL` remain active.

---

### 4.2 Single-Character Limitation of `INT 21h / AH=01h`

The critical limitation is **not the bit capacity of `AL`**, but the **input nature of `INT 21h / AH=01h`**:
- **Service `01h` only reads ONE single keyboard key per call.**
- If the user intends to enter the mark **`25`** or **`100`**:
  - `INT 21h / AH=01h` will **NOT** read `25`.
  - It reads only the first keystroke `'2'` ($50d$), echoing `'2'`.
  - The second keystroke `'5'` sits unread in the BIOS keyboard buffer until another `INT 21h` is invoked.

Therefore, **yes, the code must be completely different if you want to input multi-digit numbers (values $\ge 10$)**.

---

### 4.3 Multi-Digit Decimal Input Routine ($N \ge 10$)

To read a multi-digit number (which can span from 5 bits up to 16 bits), the program must implement an **iterative input loop**:
1. Read a single character with `INT 21h / AH=01h`.
2. Check if the user pressed the **Enter key** (ASCII `13` / `0Dh`). If yes, finish.
3. Convert character to digit: `SUB AL, 48`.
4. Accumulate into running total using:
   $$\text{Total} = (\text{Total} \times 10) + \text{New Digit}$$

#### Multi-Digit Input Algorithm in 8086 Assembly:
```assembly
; Reads an unsigned decimal number from keyboard into BX:
read_multidigit proc
    xor bx, bx         ; BX = 0 (Total accumulator)

input_loop:
    mov ah, 1          ; Read character
    int 21h
    
    cmp al, 13         ; Check if user pressed ENTER (Carriage Return)
    je done_input
    
    sub al, 48         ; Convert ASCII to digit (0-9)
    mov ah, 0          ; AX = digit value
    push ax            ; Save digit on stack
    
    ; Total = Total * 10
    mov ax, bx
    mov cx, 10
    mul cx             ; DX:AX = BX * 10
    mov bx, ax         ; BX = Total * 10
    
    pop ax             ; Restore digit
    add bx, ax         ; BX = (Total * 10) + digit
    jmp input_loop

done_input:
    ret                ; Result is in BX (can be up to 65,535!)
read_multidigit endp
```

---

### 4.4 Multi-Digit Output Differences (`DIV 10`)

Similarly, displaying values differs dramatically based on whether the number exceeds 4 bits / single digits ($> 9$):

1. **For Single Digits ($0 \le N \le 9$)**:
   - Fits in 4 bits.
   - Simply add `48`:
     ```assembly
     add al, 48
     mov dl, al
     mov ah, 2
     int 21h
     ```

2. **For Double Digits ($10 \le N \le 99$)**:
   - Spans 5 to 7 bits.
   - Cannot simply `add al, 48`!
   - Must be separated via arithmetic division `DIV 10` (as implemented in [`3.2.asm`](https://github.com/b1tranger/Microprocessor_Assembly_Lab/blob/main/LabCodes/lab-3_Arithmetic_Operations/3.2.asm) and [`4.1_CP.asm#L110-L135`](https://github.com/b1tranger/Microprocessor_Assembly_Lab/blob/main/LabCodes/lab-4_Marks_Calculation/4.1_CP.asm#L110-L135)):
     ```assembly
     mov ah, 0
     mov bl, 10
     div bl             ; AL = Tens, AH = Units
     add al, 48
     add ah, 48
     ; Print AL, then print AH
     ```

3. **For Hexadecimal Display (Base-16)**:
   - If displaying an 8-bit byte as two hexadecimal nibbles (as in [`5.1.asm`](https://github.com/b1tranger/Microprocessor_Assembly_Lab/blob/main/LabCodes/lab-5_Bitwise_Hex_Display/5.1.asm)):
     ```assembly
     ; Upper 4 bits:
     mov al, bl
     shr al, 4
     call print_hex
     ; Lower 4 bits:
     mov al, bl
     and al, 0Fh
     call print_hex
     ```

## 5. Case Study: Marks Calculation Flow in `4.1_CP.asm`

In [`4.1_CP.asm`](https://github.com/b1tranger/Microprocessor_Assembly_Lab/blob/main/LabCodes/lab-4_Marks_Calculation/4.1_CP.asm), student marks for three subjects are captured and processed:

```assembly
; 1. Input Single-Digit Marks for 3 subjects:
mov ah, 1
int 21h
sub al, 48
mov num1, al       ; e.g., 8

mov ah, 1
int 21h
sub al, 48
mov num2, al       ; e.g., 9

mov ah, 1
int 21h
sub al, 48
mov num3, al       ; e.g., 7

; 2. Add marks together:
mov al, num1
add al, num2
add al, num3
mov sum, al        ; sum = 8 + 9 + 7 = 24 (Exceeds 4 bits! 24 = 0001 1000b)

; 3. Print Total Marks (24):
; Because 24 has 2 digits, it MUST use DIV 10:
mov al, sum
mov ah, 0
mov bl, 10
div bl             ; AL = 24 / 10 = 2, AH = 24 % 10 = 4
add al, 48         ; '2'
add ah, 48         ; '4'
; Prints "24"

; 4. Calculate Average:
mov al, sum
mov ah, 0
mov bl, 3
div bl             ; AL = 24 / 3 = 8, AH = 0 (Remainder)
; Prints Average "8"
```

Notice how `4.1_CP.asm` itself proves this principle:
- Inputs are single digits ($0\text{–}9$, 4-bit magnitudes).
- Their `sum` ($24$) exceeds 4 bits.
- Because `sum` exceeds 9, the program **cannot** just `add al, 48`; it switches to `div bl` (`bl = 10`) to separate the tens and units digits!

## 6. Summary Comparison Table

| Aspect | Single-Digit Routine (Current `4.1_CP.asm`) | Multi-Digit Routine ($N \ge 10$ / $> 4$ bits) |
| :--- | :--- | :--- |
| **Input Service** | Single `INT 21h / AH=01h` call | Iterative loop calling `INT 21h / AH=01h` until Enter (`13`) |
| **Numeric Accumulation** | Direct `SUB AL, 48` | `Total = (Total * 10) + (AL - 48)` inside loop |
| **Register Storage** | Single 8-bit register (`AL`) holds $0\text{–}9$ | 16-bit register (`BX` or `AX`) holds values up to $65,535$ |
| **Bit Capacity of `AL`** | Uses lower 4 bits ($0000b\text{–}1001b$) | `AL` can hold up to 8 bits ($0\text{–}255$), but needs 16-bit registers for $> 255$ |
| **Display Method** | Direct `ADD AL, 48` | `DIV 10` repeatedly to peel off individual decimal digits |
| **Hex Alternative** | Shift nibbles directly (`SHR AL, 4` and `AND AL, 0Fh`) | Process each 4-bit nibble sequentially |
